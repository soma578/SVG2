# 06_svgmap_lightweight: SVGMap 軽量化ガイド

`docs/kairyouan.md` で整理した内容を、実装に落とし込みやすい形でまとめた。目的は **DOM と計算コストを減らし、モバイルでも詰まらない描画構成にすること**。

## 1. ゴール / KPI

- CPU 使用率を 30〜50% 削減（ズーム・パン時）
- DOM ノード数を 1/5〜1/10 に抑える（重いレイヤは Canvas / タイル化）
- モバイルで 60fps を狙う。少なくとも操作体感 0.5 秒以内
- 動的レイヤはポーリング間隔・描画方式を制御しフリーズを防ぐ

## 2. 主なボトルネック（現状の想定）

- DOM ノード増加（ポリゴン / ポイントを素直に `<path>` / `<circle>` で描く）
- 座標変換をブラウザが毎フレーム計算している
- リアルタイム API を高頻度で叩き、全件再描画している
- 大きなレイヤを一括ロードしており、視野外の領域も抱え込んでいる

## 3. 軽量化アーキテクチャの方針

- **計算と描画を分離**: 座標変換や簡略化はビルド / CLI or Worker 側で済ませ、ビューは XY を受け取って描くだけにする。
- **レイヤ単位で描画モードを選択**: 静的・枚数少は SVG、点が多い / 動くレイヤは Canvas、重いレイヤはズーム依存で非表示 or 簡略化。
- **差分更新**: 動的レイヤは「大きく動いた要素だけ更新」し、ポーリング間隔を 10〜20 秒などに制御。
- **タイル / チャンク化**: 視野内のタイルだけロード。ズーム閾値を超えたら詳細タイルを読み込む。
- **Worker 活用**: Web Worker で API 取得・座標変換・クラスタリングを実行し、メインスレッドは UI に集中。
- **region-aware 構成**: 軽量化 asset は `regions/<regionId>` 単位で持ち、切替時に全体を差し替えやすくする。

## 4. 前処理 CLI が吐くべきメタデータ（実装時に読む想定）

- **座標変換パラメータ**: `viewBox`, `worldBBoxLonLat`, `matrix` を固定値で出力。ブラウザはそのまま `transform="matrix(...)"` に流し込む。
- **レイヤ統計**: `featureCount`, `estimatedDomNodes`, `avg/maxPathPoints`, `bboxLonLat`, `suggestedRenderMode(svg/canvas/hidden)`, `notes`。
- **ズーム別簡略化プロフィール**: `zoomMin/zoomMax`, `tolerance`, `originalTotalPoints`, `simplifiedTotalPoints` を持つ配列。
- **タイル分割情報**: `layerId`, `zoom`, `bboxLonLat`, `dataFile`, `estimatedDomNodes`。視野から必要タイルを計算して取得。
- **動的レイヤ設定**: `apiEndpoint`, `pollingIntervalSec`, `maxPoints`, `cluster.enabled/radius`, `renderMode`, `fallbackRenderMode`。
- **パフォーマンスサマリ**: 前後の DOM / データサイズ、削減率。軽量化の効き具合を人間が確認するための数値。

## 5. レイヤ別の推奨描画モード（暫定）

- **L1 ベースエリア（ポリゴン系）**
  - SVG
  - 簡略化必須
  - ズームが低いときは境界線中心または弱表示
  - 必要ならズーム依存で塗りやラベル密度を制御する
  - 初期実装ではポリゴン全面タップを避け、代表点またはラベルを選択UIとして利用する
  - これにより、L1 の視認性を維持しつつ、ヒット判定と DOM 負荷を抑える
  - この選択方式は、全国規模への拡張時にも破綻しにくい保守的な基本仕様とする

- **L2 避難所（少数ポイント）**
  - WebApp Layer + SVG / HTML ピン
  - DOM 負荷が小さい範囲ではそのまま描画する
  - 施設名、収容人数、施設種別、開設状況などの属性は JSON 側に保持し、詳細表示時に参照する
  - 将来的に件数が増える場合はクラスタリングを検討する

- **L3 チーム活動（動的ポイント）**
  - 初期は WebApp Layer + SVG / HTML ピン
  - 更新頻度や件数が増えた場合は Canvas 化を検討する
  - 差分更新を前提とし、全件再描画を避ける

- **補助レイヤ（洪水・土砂などのハザード）**
  - SVG
  - 必要時のみ表示
  - 重い場合は簡略化版またはズーム閾値で制御する

## 6. ロードマップ（実装順）

1. **計測と閾値決定**
   - 現状 DOM ノード数と fps を計測し、重いレイヤを特定する。
2. **CLI メタ出力の最小実装**
   - 座標変換パラメータ + レイヤ統計 + 簡略化プロフィールを JSON に出す。
3. **描画モード分岐をフロントに導入**
   - `suggestedRenderMode` に従い SVG / Canvas / 非表示を切り替える。
4. **L1 の簡略化導入**
   - ベースエリアの表示用データを軽量化し、ズーム別の表示制御を入れる。
5. **L2 / L3 の最適化**
   - 点数が少ない段階では SVG / HTML ピンで運用し、件数増加時にクラスタや Canvas を検討する。
6. **動的レイヤの差分更新**
   - Worker で取得 + 差分更新、ポーリング間隔を制御する。
7. **最終チューニング**
   - 端末別のプロファイルを作り、モバイル用に描画密度をさらに落とす。

## 7. 実装メモ

- メタデータは `map/` か `frontend/public/regions/<regionId>/` 配下で配信すると、Next.js 側で `fetch('/regions/<regionId>/…')` しやすい。
- Canvas レイヤは `MapCanvas` とは別コンポーネントに分離し、SVG / Canvas の重ね順を明示的に制御する。
- Worker との通信は `postMessage` で `SimplifiedGeometry[]` や `ClusteredPoint[]` を渡す形を想定する。
- 初期段階では、L2 / L3 はダミーデータ運用を許容し、まず表示・選択・詳細表示を成立させることを優先する。
- current path では、publish 済み JSON がなければ `regions/<regionId>` の fallback を使う方針で region 切替を安定させる。

## 8. 現時点の改善観点

### 8.1 L1 選択方式と軽量化の整合

- L1 は面を表示し、選択は代表点またはラベルで受ける方針を維持する。
- この方式はヒット判定負荷を抑え、全国規模への拡張時にも破綻しにくい。

### 8.2 current / legacy 境界

- 軽量化対象 SVG 群は current / legacy をまたぎうる。
- current path の性能改善を優先し、legacy 資産は必要最小限の保守に留める。

### 8.3 検索と点レイヤの将来スケール

- L2 / L3 は現在の件数では SVG / HTML ピンで十分とする。
- 件数や更新頻度が増えた場合は、サーバ検索、クラスタリング、Canvas 化を段階的に適用する。

### 8.4 MapLibre 側責務整理との連動

- 軽量化施策は `MapLibreMap.tsx` の責務整理と合わせて進める。
- bridge、描画、差分更新、動的取得を分けることで、性能改善と保守性改善を両立する。

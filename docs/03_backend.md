# 03_backend: バックエンド仕様（段階的ロードマップ）

## 1. 目的

本ドキュメントは、防災マップシステムにおけるバックエンドの役割と構成を、**段階的に拡張可能な形で定義**することを目的とする。

- 初期段階では「ほぼバックエンドなし」で構成し、静的な防災マップを素早く構築する。
- その後、管理機能・検索機能・リアルタイム情報連携などを、フェーズごとに追加できるようにする。

バックエンドの詳細実装（言語・フレームワーク）は、この仕様書では固定しないが、Next.js の API Routes または Node.js/Express 等を想定して記述する。

補足:

- current path の描画責務は
  - 全国 / 都道府県 overview:
    SVGMap
  - 市区町村詳細:
    MapLibre
- ただし本書の主題は描画エンジンではなく、L2 / L3 データ供給、管理、検索、公開運用である
- 描画責務の正本は `docs/current-spec/` を参照する

---

## 2. 段階別のバックエンド構成方針

本システムのバックエンドは、以下の3段階で拡張していくことを想定する。

- **段階 0**: バックエンドなし（静的ファイル＋Next.js のみ）
- **段階 1**: 薄いバックエンド（管理・検索 API）
- **段階 2**: リアルタイム情報ハブ（災害・天気・交通 等）

それぞれの段階の仕様を以下に示す。

---

## 3. 段階 0: バックエンドなし構成

### 3.1 目的

- 可能な限りシンプルな構成で、防災マップの基本機能を動作させる。
- サーバサイドの実装負荷を抑え、UI・地図レイヤ構成・データ形式の確立に集中する。

### 3.2 アーキテクチャ

- Next.js
  - `/map` ページなどフロントエンドのみ実装
  - 静的サイト（SSG）または軽い SSR を想定
- データ
  - L1 ベースエリア: `regions/<regionId>/manifest.json` と `runtime-config.json` が指す asset
  - L2 避難所: `public/data/shelters.json` または `public/data/<regionId>/shelters.json`
  - L3 チーム活動: `public/data/team-activity.json` または `public/data/<regionId>/team-activity.json`
  - 補助レイヤ: `regions/<regionId>/...` 配下の asset を段階導入
  - Containers:
    overview / detail の責務に応じて複数 container を使い分ける
- データ取込
  - 入力元は CSV / Excel
  - 変換スクリプトにより正規化 JSON を生成する
- 地図表示
  - フロントエンドは正規化済み JSON、overview SVG、region manifest を `fetch` して表示する

### 3.3 機能面の制約

- 管理機能
  - Web からの編集は行わない
  - データ更新は CSV / Excel と SVG を Git またはファイル差し替えで運用する
- 認証
  - 管理者ログイン機能は未実装
- 外部API連携
  - リアルタイム情報は扱わない
- 初期実装では L2 / L3 はダミーデータ運用を許容する

### 3.4 段階 0 のゴール

- `/map` ページで以下が確認できる状態
  - L1 ベースエリア表示
  - L2 避難所表示
  - L3 チーム活動表示
  - 必要に応じた補助レイヤ表示
  - 選択地物の詳細表示
- データ仕様は `docs/04_data_spec.md` に従って整備されている

---

## 4. 段階 1: 薄いバックエンド（管理＋検索 API）

### 4.1 目的

- 最低限のバックエンドを追加し、
  - 管理画面からの CSV / Excel 更新
  - データ検証・プレビュー
  - 検索・フィルタの API 化
  を可能にする。
- 運用担当者が Git を直接触らなくても L2 / L3 データを更新できる状態を目指す。

### 4.2 想定技術

- 選択肢 1: Next.js の API Routes を使用
  - フロントエンドと同一リポジトリ・同一プロセスで完結
- 選択肢 2: 別プロセスの API サーバ（例: Node.js/Express, Python/FastAPI 等）
  - 将来の拡張性を優先する場合に選択
- この仕様では、エンドポイントの形のみ定義し、実装技術は後から選択可能とする。

### 4.3 エンドポイント仕様（案）

#### 4.3.1 避難所検索 API

- `GET /api/shelters`

**クエリパラメータ（案）**

| パラメータ | 型 | 説明 |
|-----------|----|------|
| `q` | string | 名称・住所などのキーワード（部分一致検索） |
| `status` | string | 避難所状態 (`open`, `closed`, `full`, `unknown`) |
| `facilityType` | string | 避難所種別 |
| `limit` | int | 取得件数上限 |
| `bbox` | string | 表示範囲のバウンディングボックス（任意） |
| `region` | string | 対象 regionId |

#### 4.3.2 チーム活動検索 API

- `GET /api/team-activity`

**クエリパラメータ（案）**

| パラメータ | 型 | 説明 |
|-----------|----|------|
| `q` | string | チーム名・活動名のキーワード |
| `status` | string | 活動状態 (`active`, `standby`, `stopped`, `unknown`) |
| `activityType` | string | 活動種別 |
| `limit` | int | 取得件数上限 |
| `bbox` | string | 表示範囲のバウンディングボックス（任意） |
| `region` | string | 対象 regionId |

#### 4.3.2b 横断検索 API

- `GET /api/search`

**クエリパラメータ（案）**

| パラメータ | 型 | 説明 |
|-----------|----|------|
| `q` | string | 横断検索キーワード |
| `limit` | int | 取得件数上限 |
| `region` | string | 対象 regionId |

#### 4.3.3 データアップロード API

- `POST /api/admin/datasets/upload`

**入力種別**
- `shelters`
- `team-activity`

**入力ファイル形式**
- CSV
- Excel (`.xlsx`)

#### 4.3.4 データ公開 API

- `POST /api/admin/datasets/publish`
  - `regionId` を受け取り、`public/data/<regionId>/...` へ公開できるようにする

#### 4.3.5 管理者ログイン API

- `POST /api/admin/login`

## 4.4 キャッシュと fallback の運用方針

- current path では、対象 region の publish 済み JSON を最優先の論理正本とする。
- フロントエンドはオンライン時に最新取得を試みる。
- 取得成功時はキャッシュを更新する。
- 取得失敗時はキャッシュを返し、キャッシュ未存在時のみ `regions/<regionId>/...` の fallback を使う。
- この方針により、ネットワーク断や一時障害時も地図表示を継続できるようにする。
- overview SVG はこのキャッシュ層の主対象ではなく、静的 asset として配信する。

## 5. 段階 2: リアルタイム情報ハブ

### 5.1 目的

- リアルタイム情報や外部データ連携を取り込み、動的防災マップへ発展させる。
- とくに L3 チーム活動の更新頻度向上、災害情報や気象情報の重ね合わせを可能にする。

### 5.2 想定機能

- L3 チーム活動データの定期更新
- 気象・河川・交通情報の外部 API 取得
- 更新時刻表示
- 差分更新
- 通知や警告表示のためのデータ供給

### 5.3 注意点

- 初期段階では未実装でよい
- 実装時はレイヤごとの更新頻度、キャッシュ、通信量制御を考慮する

---

## 6. 現時点の改善観点

### 6.1 管理認証の本番対応

- 現状の HTTP-only cookie session は開発・デモ用途としては許容する。
- 本番運用を前提とする場合、管理画面認証は早期にセッションベースまたは同等の安全な方式へ置き換える。
- `POST /api/admin/login` は将来的に単なる通過点ではなく、認可境界として扱う。

### 6.2 L2 正本データソースの固定

- L2 避難所は、region ごとにどの自治体データを正本とするのかを仕様で固定する。
- 検索 API、管理画面、公開 JSON はその正本方針に従って一貫運用する。

### 6.3 L3 更新主体と頻度

- L3 は「誰が更新するか」「どの頻度で更新するか」を仕様として明記する。
- 将来のリアルタイム化を見据えても、段階 1 で最低限の更新責任者と更新粒度を固定する。

### 6.4 検索の将来スケール

- 現状の `limit` 付き API は current path では妥当である。
- 全国規模や件数増加に備え、将来的なサーバ検索移行を前提に query 形を維持する。
